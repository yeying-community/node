# 身份凭证

本文说明 Node 身份凭证承载什么信息、由谁签发、如何验证和管理。它聚焦凭证本身及其所依据的身份事实；用户登录 Node 见[Node登录授权](Node登录授权.md)，DApp 获取获批身份资料见[DApp登录授权](DApp登录授权.md)，术语见[核心概念](../architecture/核心概念.md)。接口字段以 OpenAPI 的 Identity tag 为准。

## 身份凭证是什么

Node 当前的身份凭证是由 Node 身份 Issuer 签发的 JWT-VC（JWT 格式的可验证凭证）。它把经过验证的身份声明绑定到 Wallet Identity DID，供 Wallet 和应用按用户批准的 scope 出示。接收方应验证凭证签名、签发者、主体、类型、有效期和凭证状态，不能只解码 JWT payload 后就信任声明。

身份凭证不是 DID 私钥、Passkey、登录会话或 UCAN。它提供可验证的身份声明，不授予凭证以外的资源访问权，也不能单独证明持有人当前仍控制 DID 私钥或某个链账户。

## 当前凭证类型

授权请求中的 scope 决定是否返回相应凭证。Node 目前支持以下映射：

| Scope | 凭证类型 | 主要声明 | 声明依据 |
| --- | --- | --- | --- |
| `identity.basic` | 无独立的基础 VC | 返回 Wallet Identity DID 等基础身份结果 | DID 是身份主体；该 scope 本身不代表邮箱、账户或其他资料已验证。 |
| `identity.email` | `EmailCredential` | `email`、验证时间和验证方式 | 活跃邮箱绑定及成功的邮箱验证码验证。 |
| `identity.username` | `UsernameCredential` | `username`、限定名和策略版本 | Node 用户名 namespace 中的活跃、唯一用户名。 |
| `identity.avatar` | `AvatarCredential` | `avatarUri`、验证时间和验证方式 | 身份资料验证流程中提交并确认的头像声明。 |
| `identity.wallet` | `WalletAccountCredential` | `chainKey`、`address`、关联时间 | Node 验证 DID controller proof 与链账户控制证明后建立的活跃账户关联。 |

Passkey 不属于 VC 类型。Node 将 WebAuthn credential ID、公钥、身份 DID 和状态保存在独立的认证器记录中；Passkey 证明认证器控制权，不是对邮箱或链账户的资料凭证。

## 签发者、主体与格式

- **Issuer**：当前 Node 配置的身份 Issuer。应用通过 `/.well-known/openid-credential-issuer` 发现 issuer 和相关端点，通过 `/.well-known/jwks.json` 获取公钥。
- **Subject**：钱包身份 DID，当前形式为 `did:yeying:wid_*`。钱包地址、邮箱和用户名不是 credential subject。
- **Credential ID**：每张凭证有独立 `credentialId`，同时作为 JWT 的 `jti` 和状态查询标识。
- **声明结构**：JWT payload 中包含 `iss`、`sub`、`iat`、`nbf`、`exp`、`jti` 和 `vc`；`vc` 包含凭证类型及 `credentialSubject`。
- **签名**：Node 使用 `EdDSA` 签名，JWT header 的 `kid` 对应 issuer JWKS 中的验证密钥。
- **有效期**：默认 24 小时，签发时的上限为 7 天。有效期只约束该张凭证，不等于底层邮箱绑定或账户关联的寿命。

Node 将签发凭证记录保存到 `identity_credentials`，包括主体、类型、原始 token、状态、签发时间、过期时间和撤销时间。原始凭证会包含声明内容，因此该存储仍需按身份敏感数据保护。

## 凭证与身份事实

凭证是某一时点对身份事实的签名表达；Node 的绑定和关联记录则是签发、续签和撤销时检查的事实来源。两者不能混为一谈：凭证过期不一定表示事实失效，事实被撤销也不能靠延长旧凭证恢复。

| 声明 | Node 的事实来源 | 事实失效或变化时的处理 |
| --- | --- | --- |
| 邮箱 | `identity_email_accounts` 中该 DID 的 active 规范化邮箱绑定 | 解绑或替换绑定后，旧邮箱凭证不能继续作为当前邮箱声明。 |
| 钱包账户 | `identity_account_links` 中未撤销的账户关联 | 解绑账户后，不再据此补发该地址的凭证。 |
| 用户名 | `identity_usernames` 中 active 的 namespace/用户名记录 | 改名时旧用户名及其凭证标记为 replaced。 |
| 头像 | 未撤销的历史 `AvatarCredential` 声明 | 按当前实现的凭证记录和撤销状态管理；不能从邮箱事实推导头像。 |

同一 Node issuer 下，一个规范化邮箱最多绑定一个 active DID；一个 DID 当前只绑定一个 active 邮箱，但可以关联多个钱包账户。邮箱 OTP 证明邮箱控制权，不创建身份、不合并 DID，也不恢复身份私钥。邮箱冲突返回稳定错误码 `IDENTITY_EMAIL_ALREADY_BOUND`、`IDENTITY_EMAIL_CHANGE_REQUIRES_AUTHORIZATION` 或 `IDENTITY_EMAIL_BINDING_CONFLICT`，响应不泄露已绑定 DID。

钱包账户关联需要同时验证身份 controller 对 DID 的控制证明和账户对地址的控制证明。当前 EVM 签名消息包含完整 DID、chain key、checksum address、一次性 nonce、签发时间和过期时间；验证成功后消费 challenge。一个 DID 可关联多个账户，同一个 active `chainKey + account_id` 不能归属多个 DID。

邮箱和用户名验证通过身份 verification request/confirm 流程完成。邮箱采用 NFC 与小写规范化；用户名采用 NFC、ASCII 小写及 `a-z0-9._-` 规则，长度为 3–32，并在 issuer namespace 内唯一。验证码默认有效 10 分钟、最多 5 次错误尝试，数据库仅保存验证码 hash。其余请求字段和错误结构以 OpenAPI 为准。

PostgreSQL 启动迁移会从 active `EmailCredential` 回填邮箱绑定。若历史数据存在一邮箱多 DID、一 DID 多邮箱或与现存绑定冲突，迁移会失败关闭并输出冲突来源，不自动合并身份。运维应在启动迁移前处理冲突数据。

## 出示与验证

身份授权时，Node 根据获批 scope 选择对应凭证，只返回未撤销且未过期的 VC。缺失或过期的凭证可以基于仍有效的底层事实续签，然后再完成授权结果交换。

接收方验证凭证时至少应检查：

1. `iss` 是受信任的 Node 身份 Issuer，签名可由 JWKS 中对应 `kid` 的公钥验证。
2. `sub` 是预期的 Wallet Identity DID，`vc.credentialSubject.id` 与其一致。
3. `vc.type` 包含业务要求的具体类型，声明字段符合预期格式。
4. `iat`、`nbf` 和 `exp` 满足接受方的时间策略，且凭证尚未过期。
5. `credentialStatus.type` 为 `YeyingCredentialStatusV1`，且 `credentialStatus.id` 对应的状态是 `active`。

状态查询接口为 `POST /api/v1/public/identity/credentials/status`，以 issuer 和一组 credential ID 查询状态。当前状态包括 `active`、`expired`、数据库记录状态（如 `revoked` 或 `replaced`）和 `unknown`；状态服务不可用时返回 503，验证方不得将失败当作 active。接口返回 `checkedAt` 和 `nextUpdateAt`，缓存时间应据此限制。

## 续签、替换与撤销

授权时的自动确保流程先验证身份及其事实来源，再按 scope 检查所需凭证；已有效的凭证可复用，缺失或过期时只根据未撤销的事实生成新 VC。续签会分配新的 credential ID，并记录凭证类型和来源；邮箱凭证替换时旧记录标记为 replaced。

Wallet 主动重签通过 `credentials/reissue/challenge` 和 `credentials/reissue/confirm` 完成。Node 要求 Wallet 提交身份文档及对 challenge 的 controller proof；仅凭 DID 字符串不能申请重签。邮箱、钱包账户等凭证只能从当前 active 的邮箱绑定或账户关联重建，已撤销或已解除关联的事实不能通过续签复活。

状态查询以 `identity_credentials` 为权威。未知凭证返回 `unknown`，已过有效期返回 `expired`，撤销或替换记录返回相应状态。若状态存储不可用，Node 返回服务错误而不降级为有效。

## 安全边界

- VC 证明 Node 曾按特定流程验证某项声明，不是持续在线证明，也不保证声明在签发后永远不变。
- `identity.email` 等 scope 表示应用请求资料的范围；用户批准前应用不得假定自己已获得这些声明。
- Passkey assertion、身份 controller proof 和 VC 分别证明认证器控制、DID 控制和已验证声明，三者不可互换。
- 高风险操作仍须按各自协议再次授权；VC、普通应用会话和 UCAN 都不能替代钱包交易签名或敏感操作 proof。
- 凭证签名私钥通过加密 vault 管理，不应放入 `config.js` 或提交到仓库；运行配置和轮换规则见[加密启动](../operations/加密启动.md)。
