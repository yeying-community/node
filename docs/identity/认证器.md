# 认证器

本文说明 Node 身份登录中认证器的作用、认证证明的边界、各类密钥由谁持有，以及认证后应用获得什么。认证器是执行认证操作的设备或软件；Passkey 是认证器创建或持有的 WebAuthn 凭证，两者相关但不等同。具体接口与步骤见[Node登录授权](Node登录授权.md)和[DApp登录授权](DApp登录授权.md)；其他术语见[核心概念](../architecture/核心概念.md)。本文是安全模型说明，不重复接口字段和逐步调用说明。

## 核心结论

- 用户身份主体是 Wallet Identity DID。邮箱、链账户地址和 Passkey 都是该身份关联的资料或认证方式，不是身份主体本身。
- 用户通过认证器完成 WebAuthn 操作。WebAuthn assertion 证明本次操作使用了已登记的 Passkey credential；Node 根据 credential 与 DID 的登记关系识别身份。
- 身份认证与应用授权分开。认证成功后，Node 仍须校验应用、回调地址、请求 scope 和授权流程，才会签发授权码。
- DApp/Router 获得的是自己的应用会话，以及用户批准的身份结果；它不会因此获得钱包私钥或自动获得交易签名权。
- Passkey 平台同步与 YeYing Cloud 钱包托管是不同服务，分别管理认证器凭证和钱包密码加密的密钥备份。

## 密钥与凭证归属

| 对象 | 创建或持有方 | Node 保存或可见的内容 | 能力边界 |
| --- | --- | --- | --- |
| DID controller/recovery 密钥 | Wallet 客户端 | DID 和公开 DID Document | 控制 DID 文档、签署身份 Presentation；Node 不持有私钥。 |
| Passkey credential | 认证器创建或持有，经浏览器调用 | credential ID、公钥、RP 和状态 | WebAuthn 认证；不能代替 DID controller 签名或链上交易签名。 |
| 链账户密钥 | Wallet 客户端 | 已验证的账户关联和地址 | 证明链账户控制权、签署链上交易；Node 不持有密钥明文。 |
| 身份 VC | Node 身份 Issuer 签发 | 凭证记录和状态 | 表示经验证的邮箱、用户名、头像或账户等资料；不是私钥或应用会话。 |
| 应用会话 | DApp/Router | 不由 Node 统一管理 | 维持该应用自己的登录状态；不能代表用户授权其他资源。 |
| UCAN | Wallet 或 Node 按授权策略签发 | 验证所需 claims、issuer 或撤销元数据 | 授予特定 audience、资源和动作范围；不是用户身份私钥。 |

## 登录信任链

无钱包插件登录时，信任链可以概括为：

```text
用户通过认证器验证 Passkey
  → Node 验证 WebAuthn assertion 并识别 DID
  → 用户批准已登记应用请求的 scope
  → Node 签发一次性授权码
  → 应用后端使用 PKCE verifier 兑换授权结果
  → 应用建立自己的会话
```

WebAuthn challenge、RP ID、origin、用户验证结果和 credential 状态共同约束认证；授权码、state、回调白名单和 PKCE 约束后续交付。应用只应获得获批 scope 对应的资料。Node 登录协议见[Node登录授权](Node登录授权.md)，应用登录协议见[DApp登录授权](DApp登录授权.md)。

装有 Wallet 插件时，应用也可以走 Wallet 身份 Presentation：Wallet 使用 DID controller 对绑定 audience、nonce 和 scope 的身份出示结果签名，应用后端验证后建立自己的会话。这条路径与 Node WebAuthn 授权码流程是不同协议，不能混用两者的证明。

## 认证器、身份恢复与钱包托管

Passkey 平台同步服务由操作系统或认证器平台管理 WebAuthn 凭证。Node 作为依赖方只保存公钥等注册资料，不能读取 Passkey 私钥或控制平台账户的同步策略。

YeYing Cloud 钱包托管保存的是 Wallet 使用原钱包密码加密的密钥快照。读取快照需要身份恢复授权；解密则需要原钱包密码。Passkey 允许授权读取，不负责解密；邮箱 OTP、Node 登录会话和 DApp 会话均不等于恢复授权。细节见[钱包托管](../business/钱包托管.md)。

无插件邮箱注册也会在客户端创建 Wallet 兼容的 DID 和密钥材料。邮箱 OTP 只证明邮箱控制权；它既不生成 DID controller 私钥，也不能恢复钱包密码加密的密文。设备无法完成 WebAuthn 时，当前流程不提供 OTP-only 登录降级。

## 威胁与防护

| 威胁 | 防护机制 | 剩余风险 |
| --- | --- | --- |
| 钓鱼认证页面 | WebAuthn 将 assertion 绑定 RP ID 和 origin | 用户仍需核对授权页面展示的应用和资料范围。 |
| 断言、授权码重放 | 一次性 challenge/code、短有效期、state、PKCE | 应用必须保护 verifier 和自己的会话。 |
| 恶意应用多要资料 | 应用登记、回调白名单、scope 和用户确认 | 用户批准后，应用可按其业务和隐私策略处理已授权资料。 |
| Node 数据泄露 | Passkey 私钥和钱包密钥明文不由 Node 保存；托管密文由钱包密码加密 | 身份元数据和账户关联仍然敏感；弱钱包密码会增加离线猜测风险。 |
| 认证器或平台账户被控制 | 可撤销认证器；高风险操作应单独 step-up | 同步服务商账户安全仍由用户和平台共同承担。 |
| 应用会话被盗 | 应用应采用短期会话、撤销和安全 Cookie 等控制 | Node 的 WebAuthn 登录不能代替应用自身的会话安全。 |

登录成功只证明登录时的认证与授权条件成立，不代表用户对后续每一项高风险动作都在场。转账、身份解绑、邮箱变更、撤销认证器和托管恢复应分别使用对应的签名、step-up 或恢复协议。
