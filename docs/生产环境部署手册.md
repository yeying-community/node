# YeYing Node 生产环境部署手册

本文说明单机生产部署方式。目标主机以 Linux、Node.js 24、PostgreSQL 和 Nginx 为例，应用服务使用 `8100` 端口，Nginx 对外提供 HTTPS。使用主机防火墙或安全组限制 `8100` 仅可由本机或受控内网访问。

## 1. 部署原则

- 使用 `npm run package:release -- <tag>` 生成的发布包，不在生产主机编译源码。
- 每次发布使用独立版本目录；`current` 软链接只在发布包完整解压、配置与依赖就绪后切换。
- Nginx 负责 TLS 和公网流量；主机防火墙或安全组不应向公网开放 `8100`。
- `index.html` 不缓存；Vite 带哈希的 `/static/` 文件长期缓存且文件缺失必须返回 404。
- 密钥不写入 Git，也不写入 `config.js`；使用加密密钥文件和受限密码文件。
- PostgreSQL 使用 migration，禁止在生产打开 `synchronize`。

## 2. 主机准备

安装 Node.js 24、Nginx、PostgreSQL 客户端和基础工具：

```bash
apt-get update
apt-get install -y nginx postgresql-client ca-certificates curl
node --version
npm --version
```

创建运行用户和目录：

```bash
useradd --system --create-home --shell /usr/sbin/nologin yeying-node
install -d -o yeying-node -g yeying-node /opt/deploy/node/releases
install -d -o yeying-node -g yeying-node /opt/deploy/node/shared
install -d -m 700 -o yeying-node -g yeying-node /opt/deploy/node/shared/secrets
```

目录约定（当前生产方式）：

```text
/opt/deploy/
  node -> node-v<version>-<sha>/  当前版本软链接
  node-v<version>-<sha>/          发布包解压目录，包含 config.js、run/ 和 web/dist/
  node-v<previous>/               历史版本，供回滚使用
```

## 3. 数据库与生产配置

创建独立数据库、角色与 schema。示例：

```sql
CREATE ROLE node_user LOGIN PASSWORD '<strong-password>';
CREATE DATABASE node OWNER node_user;
\c node
CREATE SCHEMA node AUTHORIZATION node_user;
```

从发布包模板生成 `/opt/deploy/node/shared/config.js`，并确保至少满足：

```js
module.exports = {
  app: {
    env: 'production',
    port: 8100,
    corsAllowedOrigins: ['https://node.yeying.pub']
  },
  database: {
    type: 'postgres',
    host: '127.0.0.1',
    port: 5432,
    database: 'node',
    username: 'node_user',
    password: '<database-password>',
    schema: 'node',
    synchronize: false
  },
  auth: { cookieSecure: true, cookieSameSite: 'lax' },
  identity: {
    publicBaseUrl: 'https://node.yeying.pub',
    webauthn: {
      enabled: true,
      rpId: 'node.yeying.pub',
      rpName: 'YeYing Node',
      origin: 'https://node.yeying.pub'
    }
  }
}
```

按实际域名更新 CORS、WebAuthn `rpId`、`origin`、钱包身份 `publicBaseUrl`，以及 UCAN issuer 配置。钱包身份 TOTP 随身份服务启用，secret 由 Node 生成并使用 `NODE_KEY_DERIVATION_SECRET` 派生密钥加密保存。Wallet 插件内注册身份级 Passkey 时，WebAuthn 响应 origin 是 `chrome-extension://<wallet-extension-id>`；不要把它加入运行时配置，而是将正式钱包插件作为应用发布到 Node 应用中心，并把插件 origin 加入该应用的 `redirectUris`。完整字段说明见根目录 `config.js.template` 的注释。

如果启用中心化 UCAN，所有实例必须配置相同的 `issuer.baseUrl`、`allowedAudiences`、`allowedCapabilitiesByAudience` 和 active/next/previous key ring，并共享同一个 PostgreSQL schema。`ISSUER_PRIVATE_KEY` 用于新 token 签发；`ISSUER_PRIVATE_KEY_NEXT`、`ISSUER_PRIVATE_KEY_PREVIOUS` 只在轮换窗口配置，后两者是可选密钥。不要把任何私钥写进 `config.js`。

## 4. 初始化加密密钥

不要将 JWT、UCAN issuer 私钥、TOTP 存储派生根或 Webhook 主密钥写进 `config.js`。首次部署时，在受限目录生成密钥文件：

```bash
cd /opt/deploy/node
sudo -u yeying-node ./cmd secrets init
mv run/secrets.enc.json /opt/deploy/node/shared/secrets/secrets.enc.json
chmod 600 /opt/deploy/node/shared/secrets/secrets.enc.json
```

生产环境不长期保留解密密码文件。启动脚本会把 `secrets.passwordFile` 当作一次性密码文件：如果该文件已存在，启动时复用并在启动后清理；如果文件不存在，则由运维人员在终端输入 vault 密码，脚本只在启动期间创建一次性密码文件，Node 解密后会清理该文件。先准备仅运行用户可写的密钥目录：

```bash
install -d -m 700 -o yeying-node -g yeying-node /opt/deploy/node/shared/secrets
```

把 `/opt/deploy/node/shared/secrets/password` 填入共享 `config.js` 的 `secrets.passwordFile`。如需非交互升级，可在启动前由受管密钥系统短暂写入该文件；启动完成后文件会被清理。不要把密码长期保留在文件中，也不要写进 shell 历史、systemd unit 或仓库。

## 5. 构建和上传发布包

在 CI 或可信构建机执行：

```bash
npm ci
npm --prefix web ci
npm test
npm run build:all
npm run openapi:check
npm audit --omit=dev --audit-level=high
npm run package:release -- vX.Y.Z
```

将 `output/node-vX.Y.Z-<sha>.tar.gz` 上传到主机。发布包已包含 `dist/`、`web/dist/`、运行依赖描述、根目录 `cmd`、启动与健康检查脚本。

## 6. 安装和启动

在生产主机解压到新版本目录，不覆盖现有版本：

```bash
release_id="$(date +%Y%m%d%H%M%S)"
release_dir="/opt/deploy/node/releases/$release_id"
mkdir -p "$release_dir"
tar -xzf /path/to/node-vX.Y.Z-<sha>.tar.gz -C "$release_dir" --strip-components=1
chown -R yeying-node:yeying-node "$release_dir"
ln -sfn "$release_dir" /opt/deploy/node.new
mv -Tf /opt/deploy/node.new /opt/deploy/node
```

在共享 `config.js` 中配置 `app`、`database`、`secrets`、日志和生产域名等运行参数。部署目录不使用 `.env` 文件。

启动服务：

```bash
sudo -u yeying-node /opt/deploy/node/cmd service start
sudo -u yeying-node /opt/deploy/node/cmd health --level all
```

测试环境如果需要升级后自动重启，应在测试 `config.js` 中设置 `app.env: 'test'`，并用 `NODE_ENV=test ./cmd service restart` 启动；此时 `secrets.passwordFile` 会被保留并复用。

服务启动时会自动运行 PostgreSQL migration。失败时先查看 `/opt/deploy/node/shared/logs/node.log`，不要手工修改 migration 记录。

本版本的 UCAN 安全迁移会创建 `ucan_issue_sessions`、`ucan_issued_tokens`、`ucan_token_revocations` 和 `ucan_audit_logs`。启动完成后应确认 migration 已执行；不要在生产环境改用 `synchronize` 绕过迁移，也不要删除撤销表或审计表。

## 7. Nginx

示例配置 `/etc/nginx/sites-available/node.yeying.pub`：

```nginx
server {
    listen 443 ssl http2;
    server_name node.yeying.pub;

    root /opt/deploy/node/web/dist;

    location ^~ /static/ {
        try_files $uri =404;
        expires 1y;
        add_header Cache-Control "public, max-age=31536000, immutable" always;
        access_log off;
    }

    location ^~ /api/ {
        proxy_pass http://127.0.0.1:8100;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }

    location = /index.html {
        try_files $uri =404;
        add_header Cache-Control "no-cache, no-store, must-revalidate" always;
    }

    location / {
        try_files $uri $uri/ /index.html;
        add_header Cache-Control "no-cache, no-store, must-revalidate" always;
    }
}
```

检查并加载：

```bash
nginx -t
systemctl reload nginx
```

`/static/` 不能回退到 `index.html`。否则旧版本 JS/CSS 文件缺失时会得到 HTML 响应，并导致浏览器报 MIME 类型和动态模块加载错误。

## 8. 升级与回滚

升级前检查当前服务和新包：

```bash
sudo -u yeying-node /opt/deploy/node/cmd health --level all
```

按第 6 节将新包解压到新的 release 目录后，记录旧目录，再切换软链接并重启：

```bash
previous="$(readlink -f /opt/deploy/node)"
# 切换 /opt/deploy/node 到新 release 后
sudo -u yeying-node /opt/deploy/node/cmd service restart
sudo -u yeying-node /opt/deploy/node/cmd health --level all
```

若启动或健康检查失败，立即切回旧目录并重启：

```bash
ln -sfn "$previous" /opt/deploy/node.new
mv -Tf /opt/deploy/node.new /opt/deploy/node
sudo -u yeying-node /opt/deploy/node/cmd service restart
```

数据库 migration 通常不可自动回滚。涉及 schema 破坏性变更时，必须先做数据库备份并在预发布环境验证回滚策略；不要仅依赖应用目录回退。

### 8.1 Issuer 密钥轮换

执行轮换前先备份 vault，并确认所有 Node 实例使用同一数据库：

1. 写入新的 Ed25519 seed 到 `ISSUER_PRIVATE_KEY_NEXT`，滚动重启所有实例。
2. 检查 `/api/v1/public/auth/central/issuer` 返回的 `issuerKeys` 含 `active` 和 `next`，并确认下游已刷新 JWKS。
3. 将旧 active 写入 `ISSUER_PRIVATE_KEY_PREVIOUS`，把新 seed 写入 `ISSUER_PRIVATE_KEY`，再滚动重启所有实例。
4. 验证新签发 token 使用新的 active `kid`，旧 active 签发且仍未过期的 token 仍可通过 Node verifier。
5. 等待最大 token/JWT TTL、时钟偏差和下游 JWKS 缓存时间全部结束后，删除 `ISSUER_PRIVATE_KEY_PREVIOUS`；不要仅因服务已重启就删除旧 key。

轮换窗口内 `secrets:verify` 只检查 active key，`NEXT/PREVIOUS` 是否存在由上述运维步骤确认。轮换失败时先恢复旧 active，并保留旧 active 作为 previous，禁止直接清空 key ring。

## 9. 上线验收与排障

上线后至少执行：

```bash
curl -fsS https://node.yeying.pub/api/v1/public/health
sudo -u yeying-node /opt/deploy/node/cmd health --level all
curl -I https://node.yeying.pub/
curl -I https://node.yeying.pub/static/js/<current-hash>.js
```

检查要点：

- 健康接口返回 `status: ok`。
- Passkey 仅在 HTTPS 下使用，并且 `rpId`、`origin`、访问域名一致。
- `index.html` 响应不缓存；`/static/` 响应包含 `immutable`；不存在的 `/static/` 文件返回 404。
- `ISSUER_PRIVATE_KEY`、`NODE_KEY_DERIVATION_SECRET`、数据库密码和邮件 SMTP 密码不出现在日志或仓库中。
- 日志和审计表不包含明文 `sessionToken` 或 UCAN；审计只保留 token id、session hash、subject、issuer、audience 和 capabilities 等元数据。
- 撤销 session 后，已签发 UCAN 必须在 Node verifier 中立即被拒绝；多实例验收至少覆盖一个非签发实例。
- 前端更新后若旧页面加载旧分块，会自动刷新一次；静态资源 404 仍应优先检查发布目录是否完整。

更多密钥文件格式和故障定位见[加密启动](./加密启动.md)和[Node 使用指南](./Node使用指南.md)；运行参数以根目录 `config.js.template` 的注释为准。
