# 钱包身份验证与凭证 V1

邮箱和用户名验证是 Wallet identity 的独立凭证流程，不是旧 Passport 绑定，也不会创建 `sub_xxx`。

## API

```text
POST /api/v1/public/identity/verifications/request
POST /api/v1/public/identity/verifications/confirm

请求体使用 `types: ["email"]`。`types` 是一次 verification transaction 要求完成的认证集合；后续用户名、手机号或其他验证方式复用这组路径，通过数组扩展，不增加新的类型专用路径。只有集合内所有类型都实现并验证成功，事务才会签发结果。
```

请求验证码前，Node 要求该 DID 与链账户已经完成账户关联 proof。请求体包含：

```json
{
  "types": ["email"],
  "identity": "did:yeying:wid_example",
  "account": { "chainKey": "eip155:1", "address": "0x..." },
  "email": "person@example.com"
}
```

确认请求使用同一个 `verificationId`，并以 `codes` 按类型提交验证码：

```json
{
  "types": ["email"],
  "verificationId": "verification_xxx",
  "codes": { "email": "123456" }
}
```

确认成功后返回 credentials 数组。EmailCredential 使用邮箱验证码确认，UsernameCredential 使用用户名规范化和 namespace 占用确认；所有凭证的 `iss` 为配置的 issuer，`sub` 为钱包身份 DID。

一次可以提交多个类型：

```json
{
  "types": ["email", "username"],
  "identity": "did:yeying:wid_example",
  "account": { "chainKey": "eip155:1", "address": "0x..." },
  "email": "person@example.com",
  "username": "alice"
}
```

只有所有类型都成功，才会返回多个凭证。用户名在 request 阶段预留，confirm 成功后正式占用；未实现的类型会让整个事务失败。

## 安全边界

- 邮箱统一 NFC 和小写规范化。
- 验证码 10 分钟有效，最多 5 次错误尝试。
- 验证码只保存 hash，不保存明文。
- 验证成功后立即消费 challenge。
- 凭证默认有效期 24 小时，最大 7 天。
- 用户名使用 NFC、ASCII 小写和 `a-z0-9._-` 规则，长度 3-32，namespace 内唯一。

Node 已提供 `20260813090000-add-wallet-identity-state` 迁移。verification transaction、用户名预留/占用、凭证记录、完成审计、账户关联 challenge 和已验证账户均从数据库读写，支持重启和多实例。数据库不可用时身份接口直接返回 `IDENTITY_STORAGE_UNAVAILABLE`，不会降级到进程内存。验证码短期状态可增加 Redis 以降低数据库压力，但数据库是最终状态源。生产上线前还需要配置 Redis/数据库、限流、重发冷却、审计导出、密钥轮换，并完成真实数据库重启验收。SMTP 投递复用了现有邮件配置，但不复用 Passport 数据模型。
